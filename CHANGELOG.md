# Changelog

## Unreleased (contract 1)

- New `BOPS_RUN` environment variable: it names a run of its own within a worktree, apart from the worktree's run. The `/bead-loop` orchestrator claims from the main checkout, so every session a person started there shared its run, and that session's `session-start` and `sync` re-displayed and heartbeat the orchestrator's claims, hiding a dead orchestrator. An orchestrator that sets `BOPS_RUN` (for example `BOPS_RUN=bead-loop`) on every `bops` call keeps its claims in that named run, and a session without it leaves them alone and cannot release them; a person's own claims in the checkout work as before. Unset, nothing changes. **state.json is now version 5**, which a bops before this one refuses, since it would read a named run as a removed worktree's stranded holds: upgrade every bops on the machine before running this one. `/bead-loop` must set `BOPS_RUN` in its `bops` calls to benefit; until it does, it still shares the main checkout's run (bops-4ez).
- The generated bops skill (`gen cc`, `gen codex`) no longer hard-codes 120 minutes or two hours for `claim --force` and abandonment; it names `stale_minutes` (set in `.bops.json`, default 120), so it is right in a repo that sets another window. Its description and preamble now say it is not for an agent `/bead-loop` dispatched, whose orchestrator claims for it, and that a repo protocol file (`docs/agent-protocol.md`) wins on branch, worktree, landing and sync; `/bops-next` points at that file too. Regenerate a repo's installed skill to pick this up (bops-c0p).
- `bops session-start` no longer lets a slow `bd dolt pull` use up its 60 s budget, which matches Claude Code's default hook timeout. The pull now stops 25 s before the budget ends, so the hook still gets `mine`, `stale`, `ready_count` and `prime`, and the error says the pull did not finish and to run `bops sync`, which allows 2 minutes. When any command's time runs out, `bd` now gets SIGTERM and 5 s to exit before it is killed, instead of an immediate SIGKILL that could land inside a Dolt merge or commit (Windows still kills it at once). Whether `bd` stops cleanly on SIGTERM is not measured (bops-9rb).
- `bops session-start` now settles only the calling run's holds and writes nothing for another worktree's run, only listing a stranded one. `bops sync` still settles every hold in the clone against its ref (unfinished writes and deletes, lost claims, stranded holds), but repairs the ledger display and heartbeats only its own run's live holds, so a sync in one worktree no longer hides another run dying. Sync's display repair also leaves a held bead's `blocked` or `deferred` status as a person set it, repairing only the assignee and `run:` label. Sessions in one checkout still share its run, so a session in the main checkout still repairs the `/bead-loop` orchestrator's claims there (status aside) (bops-yr2).
- New `min_bops` key in `.bops.json`: the oldest `bops` release the ledger accepts. A write by an older `bops` exits 1 with the new stable code `bops_too_old` and the `go install` command that fixes it; a read answers with a warning; `bops doctor` fails a new `bops_version` check, listed only when the key is set. Only `.bops.json` may set it. A build with no version (`dev`) is not checked, and `doctor` warns. Additive, so contract 1 stands. Set it only after every machine runs this release: an older `bops` rejects the unknown key with `bad_config` on every command (bops-n4r).
- Only `.bops.json` may shorten `stale_minutes`. A user file or `BOPS_STALE_MINUTES` shorter than the repo file's value, or than the default 120 when the repo file sets none, now fails every command with `bad_config`, as `lock.mode none` and `W15` in `lint.disable` already do; either may still lengthen it. A machine with a shorter window took over other machines' claims sooner than they expected. **Before upgrading, check each machine's user file and `BOPS_STALE_MINUTES`:** one that shortens the window is refused by every command, `release` and `sync` included, until it is edited (bops-i08).
- A person can move their own held bead to another machine: `bops claim --resume <id>` now also takes a `held` bead when the claim ref names the same actor on a different machine, not only a `landing` one. Claim refs gain a `machine=` line for this; older bops ignores it. A resume is refused on the holder's own machine, for another actor, and for a held ref with no `machine` line (written by an older bops: release it there, or wait and use `claim --force`). The old machine finds out as from a takeover, in `lost_claims` at its next `sync`. Additive, so contract 1 stands: a resume that was refused is now claimed in that one case, and no output field changes. Upgrade every machine before relying on it, since only refs written by this bops name a machine (bops-xwr).

## bops 0.5.1 (contract 1) — 2026-11-20

- Two bops processes that find `events.jsonl` full at once no longer both rotate it, which could move a fresh, nearly empty file over `events.jsonl.1` and lose the old copy: rotation now takes its own lock (`events.lock`), never waiting for it, and re-checks the size under it (bops-qef).
- `blocking_labels` refuses bops's own labels (any starting `bops:`, `run:` or `pool:`), and `lint.disable` may list `W15` only in `.bops.json`, as with `lock.mode none`; a config that did either now fails with `bad_config`. `bops doctor` warns of a configured blocking label that no bead carries, such as a typo. The configuration reference notes that `.bops.json` is read from each worktree's own checkout. **Before upgrading, check `.bops.json`, the user file and `BOPS_*` env for either:** a machine whose config is newly refused fails every command, `release` and `sync` included, until it is edited (bops-jmp).

## bops 0.5.0 (contract 1) — 2026-11-20

- `sync` and `session-start` remove the per-bead lock files (`beads/<digest>.lock`) of beads no run in the clone holds, which piled up one per bead ever touched. Each is removed only while holding its lock, never waiting for it, and a command that locks a bead re-checks that its file was not removed meanwhile. `events.jsonl` logs a `bead_locks_pruned` line when a sync removed some or failed. Windows keeps its files, which are empty. **state.json is now version 4**, because bops 0.4.0 to 0.4.3 does not re-check its lock file and could lock one a prune removed: that bops now refuses the clone, so upgrade every machine's bops, and any pinned or earlier-on-`PATH` copy, before running this one. A prune runs only on a file already stamped version 4 (bops-exb).

## bops 0.4.3 (contract 1) — 2026-11-20

- A read-only command's version stamp no longer recreates a `state.json` removed since it read it, and no command saves its own actor (`BEADS_ACTOR`, or the git user) on another worktree's run that has none recorded; only the run it acts as gets that default. SPEC now says that an older bops partway through a command when the stamp lands fails with its push done, and that `bops sync` from the newer bops settles it (bops-mx0).

## bops 0.4.2 (contract 1) — 2026-11-20

- A bops that finds an older `state.json` stamps version 3 on it as soon as it opens it, read-only commands included, not at its first write. An older bops sharing the clone then refuses it from the newer one's first command instead of running beside it without the bead lock. A read-only command that cannot stamp the file (its lock busy, which it does not wait for, or the directory not writable) still reads it, and a later command stamps it (bops-j9k).

## bops 0.4.1 (contract 1) — 2026-11-19

- `events.jsonl` logs how long each command waited for and held a bead's lock (`bead_lock`, with `waited_ms` and `held_ms`), so the 10-second wait can be re-sized from real hold times. `sweep` now logs a `deferred` line when it skips a busy bead, as `sync` does, and `session-start`, `claim --force` and `claim --resume` are logged under their own names. A wait cut short by the command's own time limit is logged as `timeout` rather than `busy`. SPEC records why `sync` keeps taking every hold's lock in the clone (it is what repairs a live agent's display), and its budget line now lists `land` and `doctor`, which already had 60 seconds (bops-7uu).

## bops 0.4.0 (contract 1) — 2026-11-19

- Two bops processes on one machine no longer write one bead's claim at once. Every worktree of a clone shares its state file, and a session opened in a checkout shares that checkout's run, so a Claude session opened in the main checkout while `/bead-loop` claimed from it could run its SessionStart `sync` over the loop's work: reading a claim the loop had just moved with `note`, `land` or `release` as lost, dropping the loop's journal entry and leaving its ref with no hold, so the loop's next `note` was refused. Now `claim`, `note`, `land`, `release` and `sweep` hold an operating-system lock on the bead for the whole command and re-read the state under it; another process waits up to 10 seconds for it, then gets `ref_contention` (with `retry` advice on `claim`; a note's or release's text is kept at `saved_to`). `sweep` re-checks each bead under the lock and leaves one another session resumed or gave back after it read the refs and the ledger, rather than deleting the new claim or closing a reopened bead. `sync` settles a write in flight against the ref read under the lock, so a writer that pushed and died after sync fetched is adopted, not undone. A hold whose release never finished deleting its claim is no longer treated as held: `claim`, `note`, `land` and `release` finish that delete first, so none takes back a bead already given away. A refused or unfinished `release` keeps its text at `saved_to`, `sync` heartbeats only under the bead lock, and `land` now has a one-minute budget. `sync` and `session-start` skip a bead another process holds, and a hold whose entry changed since they read the holds, which they now do before fetching the refs; both list them in a new `deferred` field. On a file system with no file locks, commands run as before and warn. **state.json is now version 3**, so an older bops refuses it rather than race this one: upgrade every machine's bops, and rebuild every worktree's, before running the new one. The lock is released when its process exits, so a crash leaves nothing behind. Also: a claim confirmed over a release whose delete never finished is no longer deleted by the next `sync` (bops-yph).

## bops 0.3.0 (contract 1) — 2026-11-19

- `blocking_labels` in `.bops.json` lists labels that take a bead out of the pool, such as a `frozen` label a repo's loop already excludes. `bops next` leaves such a bead out under a new lint rule, W15, and `bops lint` fails it. A plain `bops claim` refuses it before taking a lock, in both lock modes; `claim --force` does not read it. Unlike every other key, each config layer adds to the list, so a user file or `BOPS_BLOCKING_LABELS` can add labels but never drop the repo's. Older binaries reject the key as unknown, so upgrade every machine on a ledger before committing it. Before, `next` offered development-collaboration's frozen beads as workable (bops-yja).

## bops 0.2.0 (contract 1) — 2026-11-17

- Release pipeline: pushing a tag `bops/vX.Y.Z` builds `bops` for linux, darwin and windows on amd64 and arm64, and android/arm64 for Termux, with the version stamped by `-ldflags -X main.version` so `bops version` prints the tag. `.github/workflows/bops-release.yml` publishes the archives and `checksums.txt` as a GitHub release, with the tag's CHANGELOG section as notes. `scripts/release-build.sh` does the build; `TestReleaseBuild` in `cmd/bops` runs it, so CI and `/verify` check every archive, the checksums and the stamped version. It is a plain `go build` with cgo off rather than goreleaser, whose free edition cannot read a `bops/`-prefixed tag. README and `bops/README.md` document the download (bops-ss6.14).
- `bops serve-mcp` is an MCP server on stdio, and `bops gen mcp` writes the tools it serves, `bindings/mcp/tools.json`. There is one tool per command with an `mcp` surface. They're read-only by default (`next`, `stale`, `lint`, `doctor`, `gates`, `deps`, `version`), and `--enable-writes` on either command adds `claim`, `note`, `release`, `land` and `sweep`. A call runs `bops <command> ... --json` with the same binary and returns its JSON document, compacted. Exit 3 is a result; exit 1 or 2 is a tool error. A result over 20 kB comes back a page at a time with a cursor that the same tool takes. The server is `internal/mcp`: JSON-RPC 2.0 over stdio, standard library only, MCP revisions 2025-06-18, 2025-03-26 and 2024-11-05, tools capability only. `scripts/check-bindings.sh` checks `bindings/mcp` (bops-ss6.12).
- `bops deps --engine cte` runs on a ledger in server mode. One recursive query through `bd sql` finds the closure both ways and the longest chain to each bead, with no fetch of the whole ledger. A chain as long as the closure is big means a cycle, and a second query then fetches the edges so the error names the cycle as `--engine bd` does. Go walks the chain with `--engine bd`'s tie-break, so both engines give the same answer. On an embedded ledger `cte` exits 1: `engine=cte needs bd in server mode`. A query that outlasts bd's 10s read timeout on the server exits 1 saying so, instead of bd's bare `invalid connection`. The id is checked before it goes into the SQL. A live test checks the two engines against each other on the 1k-node fixture and a cycle. It runs with `BOPS_INTEGRATION=1` and `BOPS_DOLT_SERVER=host:port`, and CI runs it against a `dolthub/dolt-sql-server` container. The fixture moves to `internal/depgraph/depgraphtest` so both packages share it (bops-oy9.6).
- `bops gen clj --out <dir>` generates the Clojure binding, `bindings/clojure`. `bops.clj` (namespace `bops`) has one fn per command, which shells out to `bops <command> --json` and returns `{:exit :doc :err}`, with exit 3 returned rather than thrown. A missing required option or an unknown one throws before `bops` runs. It also has a Malli schema per output, the envelope merged with the command's `output`, with `valid?` and `explain`. `bb.edn` lets `bb -e "(require 'bops)"` load it. Every result of a live run (claim, held, note, refused, released, sync, sweep, doctor and the reads) matches its schema. `bindings/kestrel/beads.clj` keeps Kestrel's policy and now makes every `bops` call through the generated namespace; its tests stub `bops/run` (bops-ss6.11).
- `bops deps <id>` reports what a bead waits on (`blocked_by`) and what waits on it (`blocks`): directly, or with `--transitive` the whole closure. `depth` is the length of the longest chain of open beads ending at it, and `--path` adds that chain (`critical_path`), computed in Go with Kahn's algorithm. The graph comes from one `bd list --all --include-gates` call: beads that are not closed, joined by `blocks`, `conditional-blocks` and `waits-for` edges, so gates count and `parent-child` does not. A cycle among the beads it waits on exits 1 naming the cycle. `--engine cte` and `--engine graph` stay reserved and exit 1: `bd sql` does not run on an embedded ledger, so `cte` waits on a bd in server mode (bops-ss6.9).
- `bops gates <id>` lists the bead's gates, open and resolved (`satisfied`), with what each waits on (`on`: a PR or run id, a timer's timeout), and its open blocking dependencies that are not gates. `bops lint <id>` now fails W05 on a bead with open gates. `bd ready` already leaves gated beads out, so `next` cannot see them; `next --include-unworkable` now looks up the beads open gates alone hold back and lists them with W05 and `blocked_by_gates`, without counting them in `excluded_count`. Default `next` makes no extra `bd` calls. `gates` joins the Claude Code skill (bops-ss6.6).
- `bops` accepts bd's JSON envelope, `{"data": …, "schema_version": 1}`, which bd 1.3.x prints with `BD_JSON_ENVELOPE=1` and bd 2.0 will print by default. `bdx.Exec` unwraps every bd output, and `ledger.DecodeIssues`, `DecodeIssue` and `DecodeCommentID` accept both forms. Before, a `BD_JSON_ENVELOPE=1` in the environment made `next`, `claim` and the rest fail with `unexpected object from bd`. Raw and enveloped fixtures from bd 1.3.4 are pinned in `internal/ledger/testdata`; the real-bd suites pass in both modes, and CI's `replicas` job now runs in both (bops-ss6.13).
- `bops gen codex --out <dir>` generates the Codex binding: the same `skills/bops/SKILL.md` prose as Claude Code, with a reference from the manifest's `codex` surfaces, and a `hooks.json` fragment (SessionStart only, upstream bd's Codex hook shape) to merge into `.codex/hooks.json`. `bindings/codex` and this repo's `.agents/skills/bops/SKILL.md` are generated and checked by `scripts/check-bindings.sh`, which replaces `check-cc-binding.sh`. The shared prose moves to `templates/skill-preamble.md`. `sweep` and `stale` gain a `codex` skill surface, since the prose uses them. The hook is unverified against a live Codex run (bops-oy9.5).
- `bops gen cc --out <dir>` generates the Claude Code binding from the manifest: `skills/bops/SKILL.md` (the hand-written preamble from `bops/internal/gen/templates/cc-preamble.md` plus a command reference, under 2k tokens), a `hooks.json` fragment with the SessionStart hook alone, and a `/bops-next` command. `bindings/claude-code` and this repo's `.claude/skills/bops/SKILL.md` are now generated, and CI and the pregate check them. `hooks.json` replaces `settings.bops.json`. SPEC §8 drops the `Stop` and `PreCompact` hooks, and the manifest's `cc` surfaces with them: Stop would run a pushing sync after every reply, and a PreCompact hook cannot reach the model. `gates` and `deps` stay out of the skill until they are implemented. `bops gen` targets that write one file still print it without `--out` (bops-ss6.10).
- Under `lock.mode: none` with no Dolt remote, `bops claim` (and `claim --force`) skips its Dolt pull and push and warns `no Dolt remote: ledger not published`, like `release`, `land`, `sweep`, `sync` and `session-start`. Before, it passed on bd's raw `Error 1105: no remote` from the pull. With a remote, a failed pull is still the `ledger not pulled` warning (bops-oy9.2).
- `bops version` reports the commit the binary was built from: `revision`, `modified` and `revision_time`, from the go command's build info. In bops's own checkout, `bops doctor` warns (exit unchanged) when the binary predates the last commit to `bops/`, with the `go install` to run. A stale binary had swept bops-oy9.4 with the pre-fix code. Additive; contract 1 is unchanged (bops-y8x).
- `.gstack/pregate.json` and `scripts/pregate-test.sh` let gstack's `/verify` run the `bops` Go tests: any file under `bops/` runs every package (the two-replica suite stays in CI), and guards run gofmt, vet, the `COMMANDS.md` sync and the `bd-lint-claim` stub tests. Docs and `.beads/` changes need no tests (bops-bj0).
- `bops sweep` removes the `bops:landing` label after it closes a bead, as SPEC §3.1 says. Before, every swept bead kept it, so `bd list --label bops:landing` returned closed beads. A removal that fails is a warning naming the command to rerun; the bead still counts as closed (bops-oy9.4).
- `bops` runs `bd` with git's automatic maintenance in the foreground (`maintenance.autoDetach=false`, `gc.autoDetach=false`, appended to any `GIT_CONFIG_*` already set). A detached `git repack -d` in Dolt's git remote cache could delete a pack while the next `bd` call read it, failing with `packfile … index unavailable`. Seen as a replicas CI flake; reported upstream as dolthub/dolt#12488 (bops-3tm).
- An invalid `.bops.json`, user config file or `BOPS_*` variable now carries the stable code `bad_config` in the result (exit 1 as before), so bindings can branch on it. The message gains a `bad_config:` prefix. Additive; contract 1 is unchanged (bops-oy9.1).
- `bops release --reason done` is refused (exit 3, `outcome: refused`) when the bead has no land record. Run `bops land` first. The check runs before the claim ref or the ledger changes, in both lock modes, and the hold is kept (bops-0g6).
- Docs: a [tutorial](docs/tutorial-first-loop.md), [how to set up the claim lock](docs/howto-claim-lock.md), a [configuration reference](docs/reference/configuration.md), an [architecture overview](docs/ARCHITECTURE.md) and a [docs index](docs/README.md). README, `bops/README.md`, CONTRIBUTING and the Claude Code binding brought up to date (bops-ilg).

## bops 0.1.0 (contract 1) — 2026-11-12

First release of `bops`, the intent-level command layer over `bd` specified in [`SPEC.md`](SPEC.md). Tag `bops/v0.1.0`. Contract 1 is frozen from this tag.

- Commands: `next`, `claim`, `note`, `release`, `land`, `sweep`, `stale`, `lint`, `sync`, `session-start`, `doctor`, `version`, `manifest`, `gen docs`. `gates` and `deps` are specified and exit 1 as not implemented.
- **Claim lock.** Ownership is a git ref per bead, `refs/bops/claims/<id>`, written with a create-only, leased push, so two machines can never both hold a bead. The ledger's assignee and `run:` label display it and are repaired by `sync`. Takeover of a stale claim (`claim --force`), PR rework (`claim --resume`), and landing refs that `sweep` deletes once the PR merges. Recovery runbook in [PROCESS.md §12](docs/PROCESS.md#12-recovery-runbook-bops-ledgers).
- `bops doctor` checks the lock remote, fetch and push access, create-only push support, and that the Dolt remote is on the same repository.
- Configuration: `.bops.json`, a per-user file and `BOPS_*` variables, validated strictly. `lock.remote` picks the lock's git remote; `lock.mode: none` turns the lock off for a single-machine ledger (repo file only). `stale_minutes`, `hold_minutes`, `pool`, `caps` and `forge` are applied.
- `claim`, `sync`, `sweep` and `doctor` refuse with `remote_mismatch` when the lock remote and the Dolt remote differ or there is no Dolt remote.
- Forge adapter for GitHub (`gh`) and GitLab (`glab`), inferred from `lock.remote`.
- `release` takes optional text with `--file <path>` or `--file -`, recorded in its `bops:released` comment. `release --reason stale` is renamed `abandoned`.
- `session-start --hook-json` emits Claude Code's SessionStart hook envelope; this repo runs it as its own SessionStart hook.
- The human-review label is spelled `needs-human` everywhere; the legacy `needs:human` is still read until v0.2.0.
- Exit 3 for a write's negative verdict (`lost`, `refused`), separate from exit 1 (could not run).
- Tests: unit and golden suites with a fake `bd`; live-ledger and two-replica race suites against real `bd` 1.3.4 in CI.
- Bindings: a hand-written Claude Code skill and hooks for the `bops` loop; the Kestrel binding claims, lands, releases and syncs through `bops`.
- ADR 0001 (derived read model, amended for the claim lock), ADR 0002 (manifest-driven Go CLI), the claim-lock design, and research on the beads pre-commit export skew.
