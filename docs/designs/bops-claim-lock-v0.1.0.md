## Problem Statement

Agents need intent-level commands over `bd`: what next, take it, record progress, give it back, prove it landed. `bops` implements those once, but it does not yet run the loop it describes.

Measured on bd 1.3.4 on 2026-11-09:

- `bops claim <id>` exits 1 on the normal path: `cannot combine --if-assignee/--if-status with --claim` (`bops/internal/intent/intent.go:207-210`). Unit tests pass because they use a fake `bd`.
- `bops release` resets status only for `blocked` (`intent.go:266-287`). A live `--reason done` run left the bead `in_progress`, unassigned, and outside `bd ready`. `done` matches SPEC §4. By code reading, `scope`, `stale` and `human` strand the bead too, which contradicts the SPEC §2 definition of release.
- `bops` is not installed on the maintainer's machine, and this repo's ledger has been driven by raw `bd`.
- `bops-ss6.1`, the P0 task that six others depend on, was claimed 2026-11-04, its lease expired minutes later, and it has no comments.
- `note land sweep stale session-start gates deps` are in the manifest but not implemented.

The deeper problem is that `bd update --claim` is atomic on one replica only. In a two-replica test, both replicas claimed one bead. A's push succeeded and B's was rejected. B then pulled, Dolt settled the assignee last-write-wins in B's favor, and B pushed. The agent told it succeeded lost the bead, and nothing told it so. Evidence: two independent runs on bd 1.3.4, both replicas on one Mac. That shows the race exists, not how often it occurs.

## What Makes This Cool

Every other small agent-coordination tool in the search results brings its own store. `bops` keeps the ledger in beads and borrows an atomic create-only ref update as a cross-machine lock, with no server and no new service. It has been tested on a local bare repo only. Whether a given forge accepts it is Open Question 1.

## Constraints

- All ledger writes go through `bd` (ADR 0001, SPEC §1.4). The lock is not a ledger write and carries no issue data.
- Go, standard library only unless justified in CONTRIBUTING.md (ADR 0002).
- bd >= 1.3; the maintainer currently runs 1.3.4.
- Must run on Termux arm64, where `git` is available.
- `claim`, `release` and `land` need the network. Offline claims are refused with `unreachable`. This was accepted with the approach. Work, `note` and sync-later still function offline. PROCESS §8 and the README change to say so.

## Premises

1. The first real user is the maintainer. `bops` has to run that loop before anyone else adopts it.
2. The loop comes first. Claim and release fixes outrank every generator and the release pipeline.
3. (Revised after the second opinion.) v0.1.0 succeeds when the Claude Code loop runs end to end on two machines AND a repeated two-replica concurrent-claim test never leaves an agent holding a success result for a bead it does not own. Clojure and MCP bindings can follow. Scope note added in spec review: an explicit `--force` takeover of an expired claim is outside "concurrent claim". The displaced holder is told at its next `sync`, `land` or `release`, and its local hold is dropped.
4. `bops stale` is a thin layer. `bd stale --status in_progress --days 1 --json` found `bops-ss6.1` on the live ledger on 2026-11-09, using synced fields. `bops` adds hour-level precision, event-based last activity and same-machine detection. ADR 0001's statement that cross-machine stale detection exists only in `bops` and bead `bops-ss6.4` are corrected to match.

## Approaches Considered

- Partition machines by `pool:`. Rejected: two machines sharing a pool still race, so the finish line narrows to partitioned use.
- Reconcile inside `bd` only (pull, claim, push, loser undoes). Rejected: the undo write can itself lose to last-write-wins, and no run has shown it converges.
- Wait for a `bd` feature (cross-replica compare-and-set). Rejected for v0.1.0: the loop cannot wait on upstream's schedule. File the request upstream; the lock is deleted the day `bd` offers this.

## Recommended Approach

Git ref as claim lock, chosen by the maintainer. Writing out the failure paths in spec review made this larger than the original estimate: plan on effort L (human: ~2 weeks / CC: ~1 day), not M.

**Lock format.** One ref per bead: `refs/bops/claims/<id>` on `origin`, the remote Dolt already uses. The value is a commit on the empty tree, created with `git commit-tree` and a message holding `run=<ulid> actor=<actor> nonce=<random> at=<iso8601>`. The nonce makes every attempt unique, because pushing an identical object reports success for both sides (reproduced) and two processes can share a run id.

**Reading locks.** `git fetch --prune origin +refs/bops/claims/*:refs/bops/seen/*` then `git for-each-ref` gives every ref's sha, run, actor and age. `sync` does this, so `next` can read the local copy without network access. `claim` and takeover write the won sha to `refs/bops/seen/<id>` with `git update-ref`, and release deletes it (`--reason done` keeps both the remote and seen refs), so the local view is right before the next `sync`.

**Local state.** `run.json` changes from a list of held ids to a map of id to `{sha, op, kind, old_run, reason}` (SPEC §3.4). An exclusive lock file per checkout, treated as abandoned when older than 5 minutes, serializes each `bops` write and every `run.json` update.

| `op` | Meaning | What `sync` does |
|---|---|---|
| `claiming` | Ref won, no ledger write yet | Resume at claim step 4 |
| `writing` | Ledger writes may exist, not published | Resume at step 6 of the sequence named by `kind` (`claim` or `takeover`), skipping writes already present |
| `held` | Claim published | Compare sha with the fetched ref |
| `releasing` | Ledger release written, not published | Push, then delete the ref with a lease unless `reason=done`, then drop the entry |
| `abandoning` | Only the ref needs removing | Delete the ref with a lease, then drop the entry |

### Claim

```
1. entry check first: fetch the ref if this run has an entry for the bead.
   op=claiming with a matching sha resumes at step 4; op=writing with a matching sha resumes at step 6;
   op=held returns outcome=lost, reason=already_held.
   No entry: bd show, check preconditions
2. create the lock commit
3. git push --porcelain origin --force-with-lease=<ref>: <sha>:<ref>
   On success, record {sha, op=claiming}
4. bd dolt pull
5. re-check preconditions
6. set op=writing, then checking the bead before each write so a resume never repeats one:
   bd update <id> --claim, add run:<ulid>, bops:claimed comment, readback
7. bd dolt push: on non-fast-forward, pull and push again, up to 5 tries with jitter
   On success, set op=held
```

The retry in step 7 is needed because every bead shares one Dolt ref, so ordinary claims on different beads reject each other's pushes. Only exhausting the retries is a failure.

Classifying step 3, from the porcelain output:

| Porcelain flag | Outcome | Measured |
|---|---|---|
| `[new reference]` | claimed, continue | 40 of 40 winners |
| `[remote rejected] (reference already exists)` | `lost` | 40 of 40 race losers |
| `[rejected] (stale info)` | `lost` | sequential loser |
| Any other `[remote rejected]` reason | Re-read the ref. If it names another attempt, `lost`. Otherwise `unreachable`, `reason=lock_unsupported` | hook refusal reported `(pre-receive hook declined)` |
| No status line | `unreachable` | not measured |

Reason strings were measured on a local bare repo. The re-read covers a forge that words them differently.

Failure paths:

- Step 4 fails with `op=claiming`: no ledger write has happened. Delete the ref with a lease and drop the entry. Result `unreachable`.
- Step 5 fails with `op=claiming`: delete the ref with a lease and drop the entry. Result `refused`.
- If either delete fails, the entry becomes `op=abandoning` and `sync` retries it.
- Step 6 or 7 fails: the ref is never deleted once a ledger write may exist. The entry stays `op=writing` and the result is `unpublished`. A resume with `op=writing` never takes the step 4 or step 5 delete paths.

### Outcomes

| Outcome | Exit | Meaning for the agent |
|---|---|---|
| `claimed` | 0 | You own it |
| `lost` | 0 | Someone else holds it, pick another bead |
| `refused` | 0 | A precondition failed after pull, pick another bead |
| `released` | 0 | The bead is released. `ref_pending: true` means `sync` will finish deleting the ref |
| `unreachable` | 1 | Could not verify, stop or retry |
| `unpublished` | 1 | Local writes are not pushed, run `sync` |

`lost` and `refused` are verdicts under SPEC §4, so they exit 0, and the JSON adds `outcome`, plus `claimed: bool` on claim. Existing precondition failures in `claim` move to this table.

### Release

Only the holder can release. The non-holder exemption for `--reason stale` at `intent.go:263` is removed, so `claim --force` is the one way to take a bead from another run. A displaced or stuck bead is taken over first, then released.

```
1. fetch the ref; if it is absent or does not match the held sha, outcome=lost, drop the entry, no ledger write
2. set op=releasing and record reason; bd writes: clear assignee, remove run labels, set status, add event comment
3. bd dolt push with the same retry
4. unless reason=done, delete the ref with a lease on the sha; then drop the entry
```

Step 3 exhausted: the ref stays, the entry stays `op=releasing`, and the result is `unpublished`. Step 4 fails: the ledger is released, so the entry becomes `op=abandoning` and the result is `released` with `ref_pending: true`. A repeat `release` resumes from the recorded `op` and never repeats ledger writes.

| Reason | Status set | Label | Ref |
|---|---|---|---|
| `blocked` | `blocked` | none | deleted |
| `scope`, `stale` | `open` | `bops:hold` | deleted |
| `human` | `open` | `needs:human` | deleted |
| `done` | unchanged, `in_progress` | `bops:landing` | kept until `sweep` |

W12 gains the `hold_minutes` window from SPEC §3.1 (it now fails forever), so held beads return to `next` when the window ends. `bops:hold` is removed by the next successful claim.

Keeping the ref on `done` stops the bead being re-claimed while its change is landing. `bops:landing` marks that state: `stale` does not report it as an orphan, and `claim --force` refuses it at any age. If the merge request is abandoned, a human removes the label, and the ordinary orphan path applies. `sweep` tolerates a missing ref.

The session protocol becomes: `claim, work, note, PR, land, release --reason done`. `sweep` closes it later.

### Takeover and orphans

An orphan is a ref with no matching ledger claim and no `bops:landing` label. It comes from a crash after step 3, a failed delete, or a `bd close` outside `sweep`.

- `stale` enumerates refs with the read above, joins them to the ledger, and adds an `orphans` output field.
- `next` excludes a bead whose locally seen ref exists and is not in a `claiming` entry being resumed by this run, as new rule W14. That covers another run's refs and this run's own orphans.
- `sweep` deletes refs for every closed bead, whoever closed it.

`claim --force` is the single recovery path for expired claims and orphans:

1. `bd dolt pull`, then `git fetch origin <ref>` for the live sha and age; an absent ref means create-only in step 3. Either failing: `unreachable`, nothing changed.
2. Evaluate on the pulled state. Refuse unless the claim is stale or the ref is an orphan older than `stale_minutes`, and refuse `bops:landing` beads. Result `refused`.
3. Replace the ref with a lease on the sha just read, or create-only if no ref exists (claims made before the lock, or by raw `bd`). A lost lease is `lost`. On success, record `{sha, op=writing, kind=takeover, old_run}`.
4. Remove old `run:` labels.
5. `bd update <id> --assignee <actor> --status in_progress --force`.
6. Add `run:<ulid>`, write `bops:claimed run=… takeover=<old-run>`, read back exactly one `run:` label equal to this run.
7. Push with the retry, then set `op=held`.

Failure at steps 4 to 7 leaves `op=writing` and returns `unpublished`, exactly as for claim. For `kind=takeover` entries, `sync` or a repeat `claim --force` follows this sequence, not the claim sequence, checking each write is absent before making it, and keeps the ref.

Step 5 was run on bd 1.3.4: from another real actor's `in_progress` claim, the command without `--force` is refused (`cannot reassign … held by`), and with `--force` the assignee transfers.

### Displaced holders

`sync` fetches before it pushes, and compares each entry's sha with the fetched ref. A held id with no fetched ref counts as lost, except `op=abandoning`, where it means the delete already happened. This check runs before any action in the `op` table.

- Lost with nothing unpublished: report it in `lost_claims[]` (exit 0) and drop the entry.
- Lost with unpublished writes: pull, then rewrite the assignee and `run:` label to the holder named in the ref commit, then push. This write converges toward the lock's holder, so it cannot compete with the new owner, who has the same values. The reason for rejecting the bd-only approach does not apply, since that undo had no arbiter.
- Lost with `op=releasing`: the correction also sets status back to `in_progress` and removes the `bops:hold`, `needs:human` or `bops:landing` label this release added, using the recorded `reason`.
- Lost with an absent ref and unpublished writes: no holder exists. Pull, clear this run's assignee and `run:` label if the ledger still carries them, push, report it in `lost_claims[]`, and drop the entry. This case does not block.
- If the correction fails, `sync` refuses to push, exits 1 and reports `blocked_push`. It fails closed rather than publishing a competing assignee.

`land` and `release` check the remote first and refuse. `note` compares the held sha with the locally seen ref, so it still works offline, and refuses when this run has no entry for the bead.

Raw `bd update --claim` bypasses the lock. The guarantee holds only for claims made through `bops`. PROCESS §2.2 and the `bdclaim` alias change to `bops claim`.

## Success Criteria

A `BOPS_INTEGRATION=1` two-replica suite, with real `bd`, a bare git remote and distinct actors, runs in CI and shows:

- Same-bead `bops claim` race, at least 40 trials: exactly one `claimed` per trial, every loser reports `outcome=lost`, and the `run:` label on both replicas equals the winner's run.
- Same-run concurrent claims in one checkout: exactly one `claimed`.
- Concurrent claims on different beads: both `claimed` and both published.
- Injected failures at claim steps 4, 5, 6 and 7, release steps 3 and 4, and takeover steps 4 to 7 reach the documented outcome, and `sync` or a repeat run converges.
- A released bead returns to `next` on the other replica after that replica syncs.
- A bead labelled `bops:landing` cannot be taken with `claim --force`, at any age.
- A displaced holder with unpublished claim writes ends with the assignee and `run:` label of the holder named by the ref on both replicas.
- A repeat claim after injected step 6 and 7 failures returns `claimed` and the ref survives, with one `bops:claimed` comment.
- Injected takeover failures resume through `sync`, and the ref is kept.
- An injected release step 3 failure with `--reason done` leaves the ref in place after `sync`.
- A displaced holder whose new holder has already released ends with no assignee from the displaced run, and `sync` does not block.
- A displaced holder with `op=releasing` leaves the new holder's status and labels unchanged.
- Comments survive: after each race, both replicas hold every event comment written by the winner.
- Release: `bd ready` includes the bead at once for `scope` and `stale`, `next` excludes it during the hold and includes it after; `needs:human` stays excluded until removed; a `blocked` bead can be re-claimed after unblocking.
- A `--force` takeover leaves one `run:` label, and the displaced run sees `lost_claims` at `sync`.

Then, outside the suite:

- The same-bead race passes once against a GitHub remote.
- This repo's own beads go through `session-start, next, claim, note, PR, land, release, sweep` on two machines.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R3-1 — consistency (blocking)

**Problem**

> A repeat claim after a step 6 or 7 failure deletes the lock over unpublished writes. The op=claiming entry does not record whether ledger writes happened, and the only resume point is step 4. After step 6 the local bead has an assignee, a run: label and status in_progress, and the preconditions refuse each of those (intent.go:197-205). So step 5 fails on the run's own writes, and the failure path deletes the ref, drops the entry and returns refused. This contradicts 'the ref is never deleted once a ledger write may exist'. The step 4 path has the same defect: 'Step 4 fails: no ledger write has happened' is false on a resume, so a failed pull there also deletes the ref. The unpublished writes then stay in the local Dolt with no entry for sync to correct, and the next sync pushes them. Step 1 also lists the precondition check before the entry branch, so the resume may refuse before reaching step 4. Sync's 'Resume at the next unfinished claim step' depends on the same missing progress information. Re-running step 6 would also add a second bops:claimed comment and rerun 'bd update --claim' on a bead this actor already holds, and neither case is defined.

**Remedy**

> Record whether ledger writes may exist, as a separate op such as claim_writing set before step 6 or a step field. Put the entry check ahead of the precondition check. On a resume after ledger writes, skip the step 5 precondition test or replace it with an ownership test that accepts this run's assignee and label, and never take the step 4 or 5 delete path. Make step 6 idempotent by checking the bead for the assignee, the label and the comment before each write. Add a repeat claim after injected step 6 and 7 failures to the suite, asserting the ref survives and the result is claimed.

### R3-2 — completeness (blocking)

**Problem**

> An interrupted takeover and an interrupted claim both record {sha, op=claiming}, so sync cannot tell them apart. The op table says sync resumes 'the next unfinished claim step'. Applied to a takeover, claim step 5 sees the old holder's assignee and run: label on the pulled bead, fails, deletes the newly replaced ref and returns refused. If it passed that test, step 6's 'bd update --claim' is the anti-steal path that the takeover's --force exists to bypass. The sentence promising that sync resumes at the first takeover step not yet done has no recorded data to act on, and the old run's id needed for 'takeover=<old-run>' is not persisted either.

**Remedy**

> Record the takeover in the entry, either as op=takeover with its own sync row or as a kind field, along with the old run id. Make sync and a repeat claim follow the takeover sequence for those entries. Have the injected takeover failures in the suite resume through sync, and assert that the ref is kept.

### R3-3 — consistency (blocking)

**Problem**

> The release sequence and the op table delete the ref unconditionally, but the reason table keeps the ref on done until sweep. The entry holds only {sha, op}, so after 'release --reason done' ends unpublished, sync cannot know the reason and deletes the ref. Release step 4 is also written with no reason condition, and 'release deletes it' in Reading locks applies the same rule to the seen ref. This contradicts 'Keeping the ref on `done` stops the bead being re-claimed while its change is landing' and makes behaviour differ between a clean done release and one that needed sync.

**Remedy**

> Add the reason, or a keep_ref flag, to releasing entries. State in release step 4, in the releasing row and in Reading locks that done drops the entry and keeps the remote and seen refs. Add an injected step 3 failure with reason done to the suite, asserting the ref survives sync.

### R3-4 — completeness (blocking)

**Problem**

> The correction needs a holder named by the ref, but the same section says 'A held id with no fetched ref counts as lost'. An absent ref has no commit to name a holder. This happens when another run took over and then released, or when sweep removed the ref of a closed bead. The design does not say what sync writes in that case. Pushing the local writes publishes an assignee and run: label for a claim nobody holds, on a bead that may have been returned to the pool or closed. Failing closed under blocked_push would wedge every future sync, because the state does not change on retry.

**Remedy**

> Define the absent-ref case: pull, then clear this run's assignee and run: label if the ledger still carries them, or discard the local writes, then push and drop the entry. Add a suite case in which the new holder has released before the displaced holder syncs.

### R3-5 — completeness (blocking)

**Problem**

> The correction covers only the fields a claim writes, but op=releasing entries also carry unpublished writes. A release whose push exhausted its retries leaves the remote showing a claim that can go stale, and claim --force can then displace it. The local release has written status open or blocked and may have added bops:hold, needs:human or bops:landing. Rewriting the assignee and run: label leaves those writes in place, and sync pushes them over the new holder. A live holder's bead could become open, blocked, held or marked landing. bops:landing would then also make claim --force refuse the bead at any age. The op table's releasing row also says to push and delete without mentioning the ownership comparison, so the two sections give different orders.

**Remedy**

> State that the displaced check runs before the op table's action, and define the correction for op=releasing so that status and the release labels are also restored to the new holder's values, or the local release writes are discarded. Add the displaced releasing case to the suite.

### R3-6 — clarity (blocking)

**Problem**

> No step of the rewritten takeover reads the ref. The earlier 'Read the current sha' step was removed, step 1 pulls only the Dolt ledger, and step 2 evaluates ledger state, yet step 2's orphan age test and step 3's lease both need the ref's sha and age. The design does not say whether this is a live fetch or the seen copy from the last sync. A stale seen copy turns a takeover of a ref that exists remotely into a create-only attempt or a stale lease, reported as lost.

**Remedy**

> Add an explicit step after the pull that fetches the ref from origin and takes the sha and age from it, and define the outcome if that fetch fails.

### R3-7 — clarity (minor)

**Problem**

> The Outcomes table defines lost as 'Someone else holds it, pick another bead', but already_held means this run holds it. An agent following the table walks away from a bead it still owns.

**Remedy**

> Note already_held in the Outcomes table, and tell the agent to continue with the bead it holds, or use a separate outcome.

### R3-8 — completeness (minor)

**Problem**

> Step 1 has no branch for op=claiming with a non-matching or absent remote sha, or for an entry in op=releasing or op=abandoning. Falling through to step 3 is probably safe because the lease arbitrates and sync handles displacement, but the document does not say so. The matching check also needs a remote read that no step names.

**Remedy**

> State the behaviour for each other entry state and name the remote read.

### R3-9 — completeness (minor)

**Problem**

> If a ref delete succeeded but its acknowledgement was lost, the leased retry targets an absent ref. An op=abandoning entry with no fetched ref also counts as lost, so sync reports a claim the run deliberately gave up in lost_claims[].

**Remedy**

> Treat an absent ref as success for op=abandoning and for the delete step of op=releasing: drop the entry with no lost_claims report.

### R3-10 — feasibility (minor)

**Problem**

> The lock is held across network calls and up to 5 pull-and-push tries, and no upper bound on that time is given. A live process that takes over 5 minutes loses exclusivity, which reopens the same-run and run.json races the lock closes. Two waiters can also both judge the lock abandoned and both take it.

**Remedy**

> Bound every git and bd call under the limit or refresh the lock's timestamp during long operations, and define an atomic takeover of an abandoned lock.

### R3-11 — clarity (minor)

**Problem**

> The column lists porcelain summary and reason text such as '[new reference]'. In git's documented format the flag is the single leading character, such as '*' or '!'. This comes from git's documentation and was not run in this review.

**Remedy**

> Rename the column to summary and say that the parser matches the summary field.

### Unresolved at the cap

1. R3-1 — consistency (blocking): A repeat claim after a step 6 or 7 failure deletes the lock over unpublished writes. The op=claiming entry does not record whether ledger writes happened, and the only resume point is step 4. After step 6 the local bead has an assignee, a run: label and status in_progress, and the preconditions refuse each of those (intent.go:197-205). So step 5 fails on the run's own writes, and the failure path deletes the ref, drops the entry and returns refused. This contradicts 'the ref is never deleted once a ledger write may exist'. The step 4 path has the same defect: 'Step 4 fails: no ledger write has happened' is false on a resume, so a failed pull there also deletes the ref. The unpublished writes then stay in the local Dolt with no entry for sync to correct, and the next sync pushes them. Step 1 also lists the precondition check before the entry branch, so the resume may refuse before reaching step 4. Sync's 'Resume at the next unfinished claim step' depends on the same missing progress information. Re-running step 6 would also add a second bops:claimed comment and rerun 'bd update --claim' on a bead this actor already holds, and neither case is defined.
2. R3-2 — completeness (blocking): An interrupted takeover and an interrupted claim both record {sha, op=claiming}, so sync cannot tell them apart. The op table says sync resumes 'the next unfinished claim step'. Applied to a takeover, claim step 5 sees the old holder's assignee and run: label on the pulled bead, fails, deletes the newly replaced ref and returns refused. If it passed that test, step 6's 'bd update --claim' is the anti-steal path that the takeover's --force exists to bypass. The sentence promising that sync resumes at the first takeover step not yet done has no recorded data to act on, and the old run's id needed for 'takeover=<old-run>' is not persisted either.
3. R3-3 — consistency (blocking): The release sequence and the op table delete the ref unconditionally, but the reason table keeps the ref on done until sweep. The entry holds only {sha, op}, so after 'release --reason done' ends unpublished, sync cannot know the reason and deletes the ref. Release step 4 is also written with no reason condition, and 'release deletes it' in Reading locks applies the same rule to the seen ref. This contradicts 'Keeping the ref on `done` stops the bead being re-claimed while its change is landing' and makes behaviour differ between a clean done release and one that needed sync.
4. R3-4 — completeness (blocking): The correction needs a holder named by the ref, but the same section says 'A held id with no fetched ref counts as lost'. An absent ref has no commit to name a holder. This happens when another run took over and then released, or when sweep removed the ref of a closed bead. The design does not say what sync writes in that case. Pushing the local writes publishes an assignee and run: label for a claim nobody holds, on a bead that may have been returned to the pool or closed. Failing closed under blocked_push would wedge every future sync, because the state does not change on retry.
5. R3-5 — completeness (blocking): The correction covers only the fields a claim writes, but op=releasing entries also carry unpublished writes. A release whose push exhausted its retries leaves the remote showing a claim that can go stale, and claim --force can then displace it. The local release has written status open or blocked and may have added bops:hold, needs:human or bops:landing. Rewriting the assignee and run: label leaves those writes in place, and sync pushes them over the new holder. A live holder's bead could become open, blocked, held or marked landing. bops:landing would then also make claim --force refuse the bead at any age. The op table's releasing row also says to push and delete without mentioning the ownership comparison, so the two sections give different orders.
6. R3-6 — clarity (blocking): No step of the rewritten takeover reads the ref. The earlier 'Read the current sha' step was removed, step 1 pulls only the Dolt ledger, and step 2 evaluates ledger state, yet step 2's orphan age test and step 3's lease both need the ref's sha and age. The design does not say whether this is a live fetch or the seen copy from the last sync. A stale seen copy turns a takeover of a ref that exists remotely into a create-only attempt or a stale lease, reported as lost.
