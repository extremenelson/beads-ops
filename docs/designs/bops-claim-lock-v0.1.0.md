## Problem Statement

Agents need intent-level commands over `bd`: what next, take it, record progress, give it back, prove it landed. The loop now runs on one machine. What remains is making a claim safe across machines.

`bd update --claim` is atomic on one replica only. In a two-replica test on bd 1.3.4, both replicas claimed one bead. A's push succeeded and B's was rejected. B then pulled, Dolt settled the assignee last-write-wins in B's favor, and B pushed. The agent told it succeeded lost the bead, and nothing told it so. That was seen in two independent runs, both replicas on one Mac, so it shows the race exists and not how often it occurs.

## What Makes This Cool

Every other small agent-coordination tool in the search results brings its own store. `bops` keeps its records in beads and borrows an atomic create-only ref update from the git remote the project already uses, with no server and no new service.

## Constraints

- All ledger writes go through `bd` (ADR 0001, SPEC §1.4). The lock is not a ledger write and carries no issue data.
- Go, standard library only unless justified in CONTRIBUTING.md (ADR 0002).
- bd >= 1.3; the maintainer currently runs 1.3.4.
- Must run on Termux arm64, where `git` is available.
- `claim`, `release` and `land` need the network. Offline claims are refused with `unreachable`. Work and `note` still function offline. PROCESS §8 and the README change to say so.

## Premises

1. The first real user is the maintainer. `bops` has to run that loop before anyone else adopts it.
2. The loop comes first. It shipped first (D28), and lock work follows.
3. v0.1.0 succeeds when the Claude Code loop runs end to end on two machines AND a repeated two-replica concurrent-claim test never leaves an agent holding a success result for a bead it does not own. Clojure and MCP bindings can follow. An explicit `--force` takeover of an expired claim is outside "concurrent claim". The displaced holder is told at its next `sync`, `note`, `land` or `release`.
4. `bops stale` is a thin layer. `bd stale --status in_progress --days 1 --json` found a stale bead on the live ledger using synced fields. `bops` adds hour-level precision and same-machine detection, and reads liveness from the lock.

## Approaches Considered

- Partition machines by `pool:`. Rejected: two machines sharing a pool still race.
- Reconcile inside `bd` only (pull, claim, push, loser undoes). Rejected: the undo write can itself lose to last-write-wins.
- Wait for a `bd` feature (cross-replica compare-and-set). Rejected for v0.1.0: the loop cannot wait on upstream's schedule. File the request upstream; the lock is deleted the day `bd` offers this.
- Ref lock with the ledger published before claim returns (the first version of this document). Rejected in D23: it needed a five-state recovery table, and three review rounds kept finding defects in it.

## Recommended Approach

**The ref is ownership. The ledger is a display that catches up (D8, D23).** Whoever's run the lock names owns the bead. The assignee, `run:` label and `bops:landing` label are written best effort, for people and for tools reading raw `bd`, which can briefly show a stale value. No ownership decision reads them. `bd ready` alone cannot say who owns a bead, so `next` reads the lock (W14).

### The lock

One ref per bead: `refs/bops/claims/<id>` on `origin`. The value is a commit on the empty tree, made with `git commit-tree`, whose message holds one `key=value` per line, split on the first `=` (D20):

```
run=<ulid>
actor=<actor>
state=held|landing
nonce=<random>
at=<iso8601>
```

The nonce is required: pushing an identical object reports success to both sides (measured on GitHub). A newline in an actor value is rejected.

Inputs and identity:

- A bead id is validated against a strict pattern before any refname is built. This does not depend on `bd show` running first.
- Lock commits use the fixed author and committer `bops <bops@invalid>`, so `user.email` is never published and machines without git identity still work.
- A ref message is untrusted input. Unknown keys are ignored, size is limited, and a malformed `at` is unknown, which never counts as stale.
- `actor` is unauthenticated free text, and anyone with push access can write these refs. The actor check on `--resume` is a safety check, not authentication.
- Claim resolves `origin` and compares it with the Dolt remote, normalizing scheme, the `git+` prefix, ssh and https spellings, and `.git`. A mismatch or a missing `origin` refuses with a stable code, because the lock must live beside the ledger.
- Lock git calls set `GIT_TERMINAL_PROMPT=0`, and add SSH `BatchMode` by extending the resolved SSH command. Setting `GIT_SSH_COMMAND` outright would replace the user's `core.sshCommand` (probed).

Every lock push is `git push --porcelain --no-verify origin --force-with-lease=<ref>:<expected> <sha>:<ref>`, with an empty `<expected>` for create-only. `--no-verify` applies only to these pushes (D19). **Never pass `-f`: it cancels the lease, and a wrong lease then succeeds (measured).**

Measured on GitHub with two clones pushing at once: exactly one winner in 40 of 40 create races and 20 of 20 takeover races. See `bops/testdata/README.md`.

**Classifying a push.** A status line of `*`, `+` or `-` is success. Reason strings differ by server, so any rejection is settled by re-reading the ref with `git ls-remote`:

| After a rejection, the ref | Create or replace | Delete |
|---|---|---|
| holds this attempt's sha | success (the acknowledgement was lost) | not gone: retry at `sync` |
| still holds the leased sha | `unreachable`: nothing changed and nobody else wrote | not gone: retry at `sync` |
| holds another sha | `lost` | `lost` |
| is absent, create | retry once, then `unreachable`, `reason=lock_unsupported` | success (already gone) |
| is absent, replace | `lost`: the ref this run leased on was deleted | success (already gone) |

The retry separates a forge that refuses custom refs from a holder who released between the push and the re-read. With no status line at all the ref is still re-read, using the same table, and a create that still has no status line after the retry is `unreachable`. A failed re-read is `unreachable`.

**One protocol for every ref write.** `internal/lock` owns this for create, note refresh, `--force`, `--resume`, the landing rewrite and delete, so no command repeats it:

1. Take the state lock, journal the intended sha, release the state lock. A new claim is `phase=pushing`. A bead already held stays `phase=held`, because its old sha is still the claim if the push never lands.
2. Push.
3. Classify by the table above. If the ref holds the intended sha, adopt it, whatever the push reported.
4. Take the state lock, record the result, release it.

`internal/lock` works through a `Git` interface and a `Journal` interface that `runstate.Store` satisfies. Refnames and the message format stay inside the package.

**Reading locks.** `git fetch --prune origin +refs/bops/claims/*:refs/bops/seen/*` then `git for-each-ref` gives every ref's sha, run, actor, state and age. `sync` does this, so `next` reads the local copy without the network. Commands that win or delete a ref update `refs/bops/seen/<id>` with `git update-ref`. A `lost` result and `--force` fetch the holder's ref with `git fetch origin +refs/bops/claims/<id>:refs/bops/seen/<id>`, because `ls-remote` returns only a sha and `update-ref` refuses an object that is not present locally (probed). That gives `lost` its actor, run and age, and it means the next `next` skips that bead. Fetch and `update-ref` run outside the state lock, so contention on a local ref is classified separately from `unreachable`.

**Local state.** Each clone has one state file and write lock, with a run per worktree (D17, D24). `Held` changes from a list of ids to a journal, the single owner of hold state: id to `{sha, intended, phase, ledger_pending, delete_pending}`, with phase `pushing` or `held`. The file gains a version and still decodes a legacy `held` list. Legacy holds have no sha and are never reported lost.

The state lock is held only around file writes, never across a network call. It carries an owner token so `Close` removes only its own lock. Every git and bd call has its own timeout, and `claim`, `release`, `note` and `sync` get a command budget above today's 30 seconds, 60 seconds for `claim` [estimated]. Cancelling a push partway would create the unknown outcome this protocol exists to resolve.

### Commands

**`claim <id>`**

1. If this run already holds the bead and `git ls-remote` shows the held sha, return `held`. A journal entry that is `pushing` follows the same read: a ref equal to its intended sha is adopted. Anything else continues to step 2, and the lease arbitrates.
2. `bd show`: check preconditions. A plain claim refuses a set assignee, a `run:` label or a status other than open, even with no ref, because a raw `bd` assignment also has no ref. The refusal names `claim --force` and the staleness window.
3. Create the ref by the protocol above. Rejected by the table above: stop, no ledger write.
4. Record the hold. If that fails, delete the ref with a lease and return non-zero. If the delete also fails, report the sha and the recovery command.
5. `bd dolt pull`. If that succeeds and the bead is no longer claimable, delete the ref and return `refused`.
6. Best effort: `bd update --claim`, add `run:<ulid>`, write the `bops:claimed` comment, push with a retry of up to 5 tries. Any failure sets `ledger_pending` and still returns `claimed`. Each write checks the bead first, so a retry adds no duplicate comment and no repeat claim.

The push retry is needed because every bead shares one Dolt ref, so ordinary claims on different beads reject each other's pushes. It no longer sits on the path that decides ownership.

**`claim --force <id>`** is the single recovery path for expired claims and orphans.

1. `bd dolt pull`, then fetch the live ref. Either failing is `unreachable`.
2. Refuse if the ref has `state=landing`. Otherwise refuse unless the staleness window has passed for one of: the ref's `at`, an orphan ref's `at`, or, with no ref, a ledger claim's `updated_at`. A future `at` is reported as anomalous and is not stale. A malformed `at` is not stale.
3. Replace the ref with a lease on the sha just read, or create-only if there is no ref.
4. Best effort: remove old `run:` labels, `bd update <id> --assignee <actor> --status in_progress --force` (measured on bd 1.3.4), add the new `run:` label, write `bops:claimed run=… takeover=<old-run>`.

The staleness window is `stale_minutes` (SPEC §10, default 120). Set it in the committed `.bops.json` so it is the same on every machine; a per-user or `BOPS_STALE_MINUTES` override shortens or lengthens only that machine's window. (Bead `bops-2cn` added the loader; v0.1.0 had a fixed 120.)

**`claim --resume <id>`** handles PR review rework (D25). Fetch the ref. It must have `state=landing`, and its `actor` must be this actor. Replace it with `state=held`, leasing on the sha just read, and record the hold. Then, best effort: remove `bops:landing`, restore the assignee and status with `bd update --assignee --status in_progress --force`, and add the `run:` label, setting `ledger_pending` on failure. Two machines sharing one actor name are separated by the ref state and the lease.

**`note <id>`** decides on the hold and the ref, not the `run:` label, so it works while `ledger_pending`. It refreshes the lock first (D27): replace this run's ref with a new commit, leasing on the held sha. A lost lease drops the hold and refuses the note, saving its text and returning the path. A network failure is a warning, so `note` still works offline. Then the existing comment and heartbeat run.

**`land <id>`** decides on the hold and re-reads the ref before writing, refusing if it no longer matches. It does not read the `run:` label.

**`release <id>`**

1. Fetch the ref. If it is absent or differs from the held sha, return `lost` and drop the hold, with no ledger write.
2. If the reason is `done`, replace the ref with `state=landing`, leasing on the held sha. Failure returns `lost` or `unreachable`, with no ledger write.
3. Best effort: the ledger writes that `release` already does.
4. Unless the reason is `done`, delete the ref with a lease. If that fails, set `delete_pending` and return `released` with `ref_pending: true`.

The non-holder path for `--reason stale` is removed, so only the holder can release. A hold stranded by a removed worktree is released from any worktree of the same clone, using the sha in the journal, or waits for `claim --force`. `claim --force` is how a bead changes hands.

**`sync`** runs `fetch --prune`, then pulls the ledger, then handles each hold in this order:

1. An intended write: promote the entry if the ref equals the intended sha. Otherwise a `phase=pushing` entry is dropped silently, with no `lost_claims` report, because this run never owned the bead. A `phase=held` entry whose ref still holds its old sha just clears the intent.
2. `delete_pending`: retry the delete, treating an absent ref as done.
3. Stranded: report it, and do not refresh or heartbeat it, so a dead worktree cannot keep a lock alive.
4. Legacy, with no sha: leave it alone.
5. Ref absent or different: report it in `lost_claims[]` and drop the hold. If the ref is absent and the bead is still in progress under this run's `run:` label and not `bops:landing`, also return it to the pool (assignee cleared, status open, label removed), because nobody holds it (`bops-ss6.25`).
6. `ledger_pending`: retry the ledger writes, checking the bead before each one.
7. Every remaining hold: compare the ledger with the ref and, if they differ, rewrite the display with `bd update --assignee --status --force` and the labels. This also undoes a displaced run's unpublished release once that run has pushed.

Then push.

**`sweep`** closes merged beads and deletes their refs. This resolves O9.

```
 bd dolt pull  --fail--> no deletes or closes this run, report
   |
 one ls-remote of the namespace, then one fetch
   |
 for each in_progress bead with landed metadata and a merged PR:
   |-- ref absent, has bops:landing --> close (crash recovery)
   |-- ref absent, no bops:landing  --> pending
   |-- state=held, or run != landed.Run --> pending, touch nothing
   +-- state=landing, run matches --> delete with a lease on the sha read
         |-- lease fails --> pending
         +-- deleted --> bd close --> push
```

Sweep reads the live ref, never `refs/bops/seen`. Delete comes before close on purpose: the lease is the single point that decides between a resume and a sweep. Once the delete wins, no resume can succeed, and a fresh claim is refused because the bead is still `in_progress`. Closing first could leave a closed bead with a live holder. Sweep no longer reads `run:` labels when a ref exists. A dry run reads and reports only.

**`stale`** reads age from the ref, falls back to `updated_at` for claims with no ref, and reports `orphans`: refs with `state=held` and no matching ledger claim. A `state=landing` ref is neither stale nor an orphan.

**`next`** excludes a bead whose locally seen ref exists and is not held by this run (W14). When the in-progress listing fails it still returns candidates, with a warning field.

### Outcomes

| Outcome | Exit | `ok` | Meaning for the agent |
|---|---|---|---|
| `claimed` | 0 | true | You own it. `ledger_pending: true` means the display will catch up |
| `held` | 0 | true | This run already owns it, so carry on |
| `released` | 0 | true | Given back. `ref_pending: true` means `sync` will finish it |
| `lost` | 3 | false | Someone else holds it, pick another bead. Carries the holder's actor, run and age |
| `refused` | 3 | false | A precondition failed, pick another bead. Carries the reason |
| `unreachable` | 1 | false | Could not verify, stop or retry. Carries a retry bound and a side-effects statement |

Exit 3 is a new negative verdict code, so `bops claim X && work` cannot proceed on a bead it does not own (final gate d2a). `emit` gains an explicit verdict path, because it ties `ok` to the error today, and SPEC §4 changes with it. Each step and outcome is appended to `events.jsonl` in the state directory, rotated at 1 MB (D21).

Contract 1 is not bumped for these changes. It is an unreleased draft with no tag and no external binding. SPEC records that waiver and freezes contract 1 at the `bops/v0.1.0` tag. `--idempotency-key` is removed from contract 1, because it has no code and the intended sha covers retries.

### Operations

- Recovery is `bops stale` plus `claim --force`. The `bd reclaim` timer is no longer recommended on bops ledgers, because it ignores the lock (D18).
- PROCESS gains a recovery section for stuck states (D22). An abandoned PR on a landing bead is handled there with `claim --resume` under the holder's `BEADS_ACTOR`, then `release`.
- Raw `bd update --claim` bypasses the lock. The guarantee holds only for claims made through `bops`. `/bead-loop` and Kestrel still claim through raw `bd`, so they are outside the v0.1.0 guarantee until `bops-ecs` moves them.
- Upgrade every machine before the first claim on the new version, because an old binary ignores the lock.
- A ledger used on one machine can turn the lock off with `lock.mode: none` in the committed `.bops.json` (bead `bops-4lv`, gate decision d4a). Commands then decide ownership from the ledger alone (`bd update --claim`, the `run:` label and assignee, `updated_at`), touch no ref and no remote for locking, and warn `lock.mode is none` on every result; `claim --resume` is refused and `doctor` skips every check. Only the repo file may set `none`, because one machine of a shared ledger turning it off would lose that machine's protection silently. The rules are SPEC §3.0.

## Success Criteria

A `BOPS_INTEGRATION=1` two-replica suite with real `bd` and a bare git remote, running in CI:

- Same-bead `bops claim` race, at least 40 trials, for distinct actors and for one shared actor: exactly one `claimed` per trial, every loser `lost` with `ok:false` and exit 3, the ref names the winner, and the loser wrote nothing to the ledger after both sides sync. 40 clean trials bound the failure rate only to about 7.5% at 95% confidence [estimated], so the suite is an integration check and the server's compare-and-swap is the guarantee.
- Same-run concurrent claims: one `claimed`, the other `held`.
- Concurrent claims on different beads: both `claimed`.
- Multiple worktrees, including one removed while holding a claim.
- A slow, failing pre-push hook does not affect claims.
- A failed ledger write leaves `claimed` with `ledger_pending`, and `sync` repairs it.
- `--force` takeover: exactly one winner, and the displaced run sees `lost_claims` at `sync`.
- `--resume` by the same actor works, and another actor is refused.
- A run that notes every hour is not stale at two hours, and offline `note` still succeeds.
- Injected failures at each ref push and ledger step reach the documented outcome, and `sync` or a repeat run converges. That includes a lost acknowledgement on every kind of ref write and a crash after a push.
- A failed `bops:landing` label write leaves `--force` refused, and a second machine sharing the actor cannot displace a resumed holder.
- Each `sweep` branch, a sweep from a stale replica, a resume racing a sweep, and a crash between delete and close.
- `lost` followed by `next` returns a different bead.
- `note` works while `ledger_pending`.
- A displaced run's unpublished release does not stick after both sides sync.
- N worktrees claim at once against a slow remote with no state lock failure.
- A legacy state file with a non-empty `held` list loads.

Each case has its value card in the eng test plan at `~/.gstack/projects/extremenelson-beads-ops/anelson-plan-bops-v0.1.0-ceo-review-eng-review-test-plan-20261110-090551.md`. CI pins bd 1.3.4 and sets an explicit `go test -timeout`. The suite records claim latency.

### R3-1 — consistency (blocking)

**Problem**

> A repeat claim after a step 6 or 7 failure deletes the lock over unpublished writes. The op=claiming entry does not record whether ledger writes happened, and the only resume point is step 4. After step 6 the local bead has an assignee, a run: label and status in_progress, and the preconditions refuse each of those (intent.go:197-205). So step 5 fails on the run's own writes, and the failure path deletes the ref, drops the entry and returns refused. This contradicts 'the ref is never deleted once a ledger write may exist'. The step 4 path has the same defect: 'Step 4 fails: no ledger write has happened' is false on a resume, so a failed pull there also deletes the ref. The unpublished writes then stay in the local Dolt with no entry for sync to correct, and the next sync pushes them. Step 1 also lists the precondition check before the entry branch, so the resume may refuse before reaching step 4. Sync's 'Resume at the next unfinished claim step' depends on the same missing progress information. Re-running step 6 would also add a second bops:claimed comment and rerun 'bd update --claim' on a bead this actor already holds, and neither case is defined.

**Remedy**

> Record whether ledger writes may exist, as a separate op such as claim_writing set before step 6 or a step field. Put the entry check ahead of the precondition check. On a resume after ledger writes, skip the step 5 precondition test or replace it with an ownership test that accepts this run's assignee and label, and never take the step 4 or 5 delete path. Make step 6 idempotent by checking the bead for the assignee, the label and the comment before each write. Add a repeat claim after injected step 6 and 7 failures to the suite, asserting the ref survives and the result is claimed.

### R3-2 — completeness (blocking)

**Problem**

> An interrupted takeover and an interrupted claim both record {sha, op=claiming}, so sync cannot tell them apart. The op table says sync resumes 'the next unfinished claim step'. Applied to a takeover, claim step 5 sees the old holder's assignee and run: label on the pulled bead, fails, deletes the newly replaced ref and returns refused. If it passed that test, step 6's 'bd update --claim' is the anti-steal path that the takeover's --force exists to bypass. The sentence promising that sync resumes at the first takeover step not yet done has no recorded data to act on, and the old run's id needed for 'takeover=<old-run>' is not persisted either.

**Remedy**

> Record the takeover in the entry, either as op=takeover with its own sync row or as a kind field, along with the old run id. Make sync and a repeat claim follow the takeover sequence for those entries. Have the injected takeover failures in the suite resume through sync, and assert that the ref is kept.

### R3-3 — consistency (blocking)

**Problem**

> The release sequence and the op table delete the ref unconditionally, but the reason table keeps the ref on done until sweep. The entry holds only {sha, op}, so after 'release --reason done' ends unpublished, sync cannot know the reason and deletes the ref. Release step 4 is also written with no reason condition, and 'release deletes it' in Reading locks applies the same rule to the seen ref. This contradicts 'Keeping the ref on `done` stops the bead being re-claimed while its change is landing' and makes behaviour differ between a clean done release and one that needed sync.

**Remedy**

> Add the reason, or a keep_ref flag, to releasing entries. State in release step 4, in the releasing row and in Reading locks that done drops the entry and keeps the remote and seen refs. Add an injected step 3 failure with reason done to the suite, asserting the ref survives sync.

### R3-4 — completeness (blocking)

**Problem**

> The correction needs a holder named by the ref, but the same section says 'A held id with no fetched ref counts as lost'. An absent ref has no commit to name a holder. This happens when another run took over and then released, or when sweep removed the ref of a closed bead. The design does not say what sync writes in that case. Pushing the local writes publishes an assignee and run: label for a claim nobody holds, on a bead that may have been returned to the pool or closed. Failing closed under blocked_push would wedge every future sync, because the state does not change on retry.

**Remedy**

> Define the absent-ref case: pull, then clear this run's assignee and run: label if the ledger still carries them, or discard the local writes, then push and drop the entry. Add a suite case in which the new holder has released before the displaced holder syncs.

### R3-5 — completeness (blocking)

**Problem**

> The correction covers only the fields a claim writes, but op=releasing entries also carry unpublished writes. A release whose push exhausted its retries leaves the remote showing a claim that can go stale, and claim --force can then displace it.
