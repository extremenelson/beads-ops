# Project beads into Datalog; never replace Dolt

**Recommendation: yes, add a local graph layer, but strictly as a rebuildable read model owned by the Clojure orchestrator, built on Datalevin (EPL-2.0, embedded, Datalog rules), fed from `bd export` plus the beads events journal, and never used as a source of truth or a sync channel.** The premise of the original question is stale: current beads (v1.3.4, released 2026-11-04) stores issues in Dolt, not JSONL+SQLite; `.beads/issues.jsonl` is "an export for viewers and interchange, explicitly not the source of truth" ([beads README](https://github.com/gastownhall/beads)), and the project's own history shows it tried and abandoned the two-store "canonical file + local cache" design over delete/drift reconciliation ([DoltHub, 2026-04-02](https://www.dolthub.com/blog/2026-04-02-restoring-beads-classic/)). Because Dolt already provides versioned history, cell-level merge, and multi-machine sync via `refs/dolt/data` on the git remote, a graph database adds nothing to sync or durability; what it adds is the general graph query surface beads lacks (`bd query` has no edge predicates; there is no path, critical-path, or cross-type transitive query) and insulation from a fast-churning upstream behind the stable `--json` and journal contracts. Datalevin beats the alternatives for this reader because the orchestrator is Clojure, Datalog rules express mixed-edge transitive closure directly, the rule engine is fast on recursive queries (sub-second on ~277k edges, self-reported), it ships a read-only-by-default MCP server, and Node/Python bindings exist for the TypeScript side ([Datalevin](https://github.com/juji-io/datalevin)). The strongest alternative is building no graph engine at all and answering everything with `bd sql`/SQLite recursive CTEs plus application code, which is adequate up to tens of thousands of nodes; switch to it if the Clojure orchestrator is not the hub of your tooling. Two assumptions remain unvalidated as of 2026-11-04: whether beads events-journal sequence numbers survive `bd dolt pull` across machines (design around it with full re-projection after pull), and whether Datalevin 1.2.x safely permits a second read-only process on the same directory (design around it with a single owner process).

## The premise is eight months stale, and the leases dispute is a version skew

Three of the four research notes were written against different beads snapshots, and the differences matter for the decision. The candidates survey cites beads v0.49.5 (2026-02-08) and describes "JSONL in `.beads/` with a SQLite cache" ([pkg.go.dev](https://pkg.go.dev/github.com/steveyegge/beads@v0.49.5)). That design ended six days later: Dolt became the default in **v0.50.0 (2026-02-14)**, which also removed the daemon/RPC subsystem (~19,663 lines) and the JSONL sync layer (~7,634 lines); the SQLite backend was deleted outright in **v0.58.0 (2026-03-02)**, and a 2026-07 proposal for Postgres/MySQL/SQLite adapters was rolled back before any tagged release, with `beads.go` now refusing metadata that names those as backends ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md); [PROPOSAL-pluggable-storage-backends](https://github.com/gastownhall/beads/blob/main/PROPOSAL-pluggable-storage-backends.md)). Dolt is pinned at 2.6.0, every write auto-commits to Dolt history, and JSONL export "do[es] not capture Dolt branches, full commit history, working-set state, or non-issue tables" ([docs/architecture/dolt.md](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md)). The only lineage that still runs the JSONL+SQLite model is the community Rust port `br` (0.7.6), whose README is candid that keeping the two stores aligned required three-way merge against a base snapshot, tombstones, bounded history, explicit `--reconcile`, and refusal when both sides changed ([beads_rust README](https://docs.rs/crate/beads_rust/latest/source/README.md)). Anyone proposing to make a graph DB canonical over a file export should read that README as the bill of materials.

The notes also disagree on whether beads has claim leases, heartbeats, and compare-and-set. The architecture note says yes; the prior-art note says "Beads still lacks leases/heartbeats." Both are correct for their snapshot. **Leases, heartbeats, and CAS shipped in v1.3.0 on 2026-09-15**, whose headline is "HTTP API server (`bd serve`), a multi-agent coordination layer with claim leases and compare-and-set updates, and `bd sync` for federation"; `bd heartbeat` refreshes a TTL lease, `bd reclaim` reverts stale claims, and `bd update` accepts `--if-assignee` and `--if-revision` guards ([GitHub releases](https://github.com/gastownhall/beads/releases); [docs/cli-reference/heartbeat.md](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/heartbeat.md)). The prior-art note's claim rests on the FAQ and coordination pages, which do not mention leases, and on a third-party September 2026 snapshot whose last observed commit was 2026-07-15, two months before 1.3.0 ([beads FAQ](https://beads.gascity.com/reference/faq.md); [brightcoding, 2026-09-30](https://blog.brightcoding.dev/2026/09/30/gastownhallbeads-persistent-graph-memory-for-ai-coding-agents)). The reconciled statement is: beads v1.3.x has leases, but they are deliberately **node-local**: "Leases live in an ephemeral, node-local table: heartbeats write no Dolt commit... Leases are only enforceable on the node that granted them; cross-machine claim visibility rides the issue's status and assignee, which do commit" ([heartbeat.md](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/heartbeat.md)). Gas City's own comparison says the same ([beads vs br](https://gascity.com/guide/beads-vs-br/)). For the multi-developer, multi-machine requirement this is the single most consequential fact in the notes: a crashed agent on machine A leaves an `in_progress` issue that machine B's `bd reclaim` cannot see as expired, so beads-ops must implement its own stale-claim detection over the synced fields (`status`, `assignee`, `updated_at`), and that detector is a natural first query for the graph layer.

One further premise correction: the project is not a Yegge side project anymore. Releases are gated by Gas City, Inc.'s 155-job RC Gate, the roadmap owner is a Gas City CTO, and the next two roadmap items are "Versioned beads and history" with `expectedRevision` CAS and "Beads Graph Preview 2," a generic typed Bead-and-Link graph model served over the draft BDP protocol from SQL-server workspaces only ([ROADMAP.md](https://github.com/gastownhall/beads/blob/main/ROADMAP.md); [gastownhall/bdp](https://github.com/gastownhall/bdp)). Upstream is converging on its own graph store. That is an argument for keeping your layer thin, read-only, and retirable, not for skipping it: the in-tree design explicitly leaves "Issues / Dependencies / wisps — the existing issue stack. Unchanged, not served over BDP in v0" ([engdocs/BDP_GRAPH_ARCHITECTURE.md](https://github.com/gastownhall/beads/blob/main/engdocs/BDP_GRAPH_ARCHITECTURE.md)), and Thoughtworks' Trial-ring note (Nov 2026) warns that "clients on different versions can't share a store" and "teams should pin one version per shared store" ([Thoughtworks Radar](https://www.thoughtworks.com/pt-br/radar/tools/beads)).

## A derived read model is the only architecture that does not fight Dolt

The decision between "graph DB as source of truth" and "graph DB as derived read model" is not close. Dolt gives you, in one artifact, SQL, full commit history, cell-level three-way merge, and push/pull to the same git origin the code uses ([docs/core-concepts/sync-concepts.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md)). None of the embeddable graph engines is mergeable: Datalevin's LMDB files, LadybugDB's columnar store, DuckDB files, and XTDB's Arrow segments are all opaque binaries. A write-through graph layer would therefore have to re-solve multi-machine merge, re-implement hash-ID assignment, cycle rejection, blocking-hierarchy validation, close policy, and lease arbitration that `bd` performs on write, and would collide with BDP. The beads maintainers say so directly: custom tables through direct storage access "are a legacy SQLite-only pattern," and the current guidance is to "keep extension state outside the beads database and connect it to beads through stable CLI surfaces" ([docs/reference/advanced.md](https://github.com/gastownhall/beads/blob/main/docs/reference/advanced.md)). The community ecosystem of roughly 25 listed tools follows the same rule: almost all read and write "exclusively through `bd --json`," several tail `bd events`, and the few that read Dolt SQL directly still write through `bd` "to preserve hook logic and ID assignment" ([docs/community-tools.md](https://github.com/gastownhall/beads/blob/main/docs/community-tools.md)).

The sanctioned feed for an external index is exactly what a projection needs. The **events journal** (first in CHANGELOG at v1.2.1, actor attribution added in 1.3.0) is "one workspace-wide, sequence-ordered stream of committed mutations, replayable from a checkpoint... The spirit is a binlog, not a notification," intended for "a machine keeping its own copy of the graph in step" ([docs/reference/events-journal.md](https://github.com/gastownhall/beads/blob/main/docs/reference/events-journal.md)). It is off by default, must be enabled at every writer, and auto-prunes at 7 days or 100,000 rows. The projection pipeline is therefore: baseline from `bd export --all` (JSONL, one row per issue with dependencies, labels, comments inline), then tail `bd events export` from a stored cursor, applying each mutation to the Datalog store; `rebuild = truncate + replay`, drift check = rebuild into a temp DB and diff, which is the Fossil/git-bug/event-sourcing pattern the modeling note documents ([Fossil bugtheory](https://www.fossil-scm.org/home/doc/tip/www/bugtheory.wiki); [Fowler](https://martinfowler.com/eaaDev/EventSourcing.html)). Beads already maintains one derived graph property itself, the `is_blocked` column repaired by `bd recompute-blocked` ([CHANGELOG 1.3.0](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)); your projection generalizes that pattern rather than inventing a new one.

The unvalidated assumption here is cross-machine journal continuity. The docs describe the journal as workspace-wide and sequence-ordered but do not say whether journal rows replicate through `bd dolt pull`, nor how sequence numbers behave after a merge brings in another machine's commits; a known 1.3.x bug already produces clones with an "empty `events` table" after adopting migration 0062 via pull or bootstrap ([CHANGELOG 1.3.3-rc.1](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)). The frugal design is to treat the journal as a *local* incremental feed only, and to trigger a full re-projection from `bd export --all` after every `bd dolt pull`, `bd bootstrap`, or any journal gap. At the sizes involved (thousands of issues) a full rebuild is sub-second; grite reports a 500 ms rebuild from 10k events on a comparable design ([dev.to, grite](https://dev.to/dipankar_sarkar/two-coding-agents-editing-the-same-issue-no-merge-conflict-here-is-how-git-refs-make-that-work-325k)), so you lose nothing by being conservative. Watermarks ("what changed since my last session") should be stored per machine alongside the projection, not in beads.

Schema for the projection is dictated by what the sources agree on. Every production tracker examined stores a node table plus a typed, directed edge table with inverses derived, not stored (Linear's `IssueRelationType` has no `blockedBy`; "blocked by" is computed from inverse relations) ([linear-api relations.rs](https://docs.rs/linear-api/latest/src/linear_api/relations.rs.html)). In Datalog that is one entity per issue with its scalar attributes, one `:edge/*` entity per `(src, dst, type)` triple carrying `created_at`/`created_by`, label as a cardinality-many attribute, comments as component entities, and `:event/*` entities straight from the journal with `actor`, `seq`, and the mutated field. Beads' ten dependency types (four blocking: `blocks`, `parent-child`, `conditional-blocks`, `waits-for`; six non-blocking: `related`, `tracks`, `discovered-from`, `caused-by`, `validates`, `supersedes`) plus four graph links (`replies-to`, `relates-to`, `duplicates`, `supersedes`) and gates all fit that one edge table ([docs/core-concepts/dependencies.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md); [graph-links.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/graph-links.md)). Anything beads-ops needs that beads does not model (artifact links to commits/PRs/files, template provenance beyond `SourceFormula`, lint verdicts) belongs in beads' free-form `metadata` JSON, which is the documented extension point ("prefer the `metadata` field for integration-, orchestrator-, or team-specific data before proposing new first-class fields") ([docs/core-concepts/metadata.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/metadata.md)), and the projection lifts those keys into attributes. Node-local ephemeral state (session caches, the orchestrator's own lease shadow) stays in separate attributes never written back, mirroring beads' wisp/`dolt_ignore` pattern.

## Datalevin wins on fit; the real contest is against "no engine at all"

The candidates survey is unusually clear once the dormant and non-open-source options are removed. Kùzu was archived 2025-10-10 at v0.11.3, its MCP server the same day, and the Kineviz "bighorn" fork is itself archived ([The Register, 2025-10-14](https://www.theregister.com/2025/10/14/kuzudb_abandoned/); [kineviz/bighorn](https://github.com/kineviz/bighorn)); CozoDB's last crate release is 0.7.6 from 2023-12-11 with zero issue activity ([crates.io](https://crates.io/api/v1/crates/cozo/versions); [SourcePulse](https://www.sourcepulse.org/projects/1251846)); Memgraph, FalkorDB, and SurrealDB are BSL/SSPL, not OSI open source ([isitreallyfoss](https://isitreallyfoss.com/projects/memgraph/); [FalkorDB license](https://docs.falkordb.com/license.html); [surrealdb.com/license](https://surrealdb.com/license)); Neo4j embedded is GPL and forbids concurrent instances on the same files; TypeDB and Apache AGE require a server. That leaves four serious embedded candidates and one honest null option.

Heavy JVM footprint; redundant with Dolt. |

The case for rank 1 over rank 2 is specific, not generic. Datomic staff warned a decade ago that recursive rules work cleanly "if all the links use the same attribute" and get "complicated beyond two or three link types" ([Datomic forum](https://forum.datomic.com/t/how-to-do-graph-traversal-with-rules/132)); beads has four blocking edge types with different semantics (`waits-for` is fan-in on children; `conditional-blocks` fires only if the predecessor fails; `parent-child` propagates the parent's deferred/blocked state), and SQL recursive CTEs handle that even worse because the recursive step "sees only the single row being expanded," so DAGs re-expand shared nodes once per path and "constrained path queries, such as paths where every intermediate node has a given type, are painful in SQL compared with Cypher" ([SQLite forum](https://sqlite.org/forum/forumpost/cd5ff0a1d4?t=h&unf); [ctxgraph](https://dev.to/rohansx/sqlite-as-a-graph-database-recursive-ctes-semantic-search-and-why-we-ditched-neo4j-1ai)). Datalog rules with a single generic `:edge/type` attribute and per-type rule heads (rule heads "can be defined multiple times" as logical OR) sidestep both problems ([Datomic query reference](https://docs.datomic.com/query/query-data-reference.html)), and Datalevin's 2026 engine makes them cheap. The honest counterweight is that every Datalevin performance number in the notes is the author's own benchmark with no independent replication, Datalevin removed multi-process WAL sharing in 1.2.0 (so only one process may own the directory), and a March 2026 report of corruption from two JVMs opening the same files predates that change ([Clojurians log 2026-03-24](https://clojurians-log.clojureverse.org/datalevin/2026-03-24)). Both constraints are satisfied by the architecture already chosen: the orchestrator is the sole writer and the sole opener; everyone else goes through it.

Datalog also has one thing none of the Cypher engines offers for this use: the queries are data. A beads-ops lint rule ("no claim while any `blocks` or `waits-for` predecessor is open," "no close while a `gate` child is unsatisfied," "formula has a dead step") is an EDN rule set that ships in the repo, is diffable, and is reusable from Clojure, from the Node binding, and from `dtlv` on the command line.

## Sync stays in Dolt; the graph layer carries only a per-machine watermark

The multi-developer, multi-machine requirement is met entirely by beads' own supported pattern, and the graph layer must not attempt to improve on it. The pattern is one shared Dolt remote on the project's git origin (`refs/dolt/data`), `bd bootstrap` on every fresh clone, `bd dolt push` before leaving a machine and `bd dolt pull` before creating work, non-fast-forward push rejection resolved by pull-then-push, and `bd doctor --fix` for the residual conflicts ([docs/architecture/index.md](https://github.com/gastownhall/beads/blob/main/docs/architecture/index.md); [DoltHub common beads workflows, 2026-04-15](https://www.dolthub.com/blog/2026-04-15-common-beads-workflows/)). On each machine, embedded mode is single-writer via file lock and pays engine startup per `bd` command; a Clojure orchestrator driving several local agents should run `bd init --server` (or the shared `~/.beads/shared-server/`) so concurrent local writers do not hit "database is locked," and should prefer `bd serve`'s HTTP API over forking a subprocess per call ([docs/architecture/dolt.md](https://github.com/gastownhall/beads/blob/main/docs/architecture/dolt.md); [docs/cli-reference/serve.md](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/serve.md)). This matches the preference for git-only multi-machine sync without a cloud layer, because Dolt rides the git remote you already push to.

Three hazards are documented and belong in the beads-ops process doc rather than in code. First, version skew: "a mixed-version fleet [is] a broken fleet: one machine running 1.3.0 takes the whole store forward and every 1.2.2 client stops," so pin one `bd` version per project and use the designated-migrator procedure (one clone migrates and pushes, the rest `bd bootstrap`) ([CHANGELOG 1.3.0](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)). Second, Dolt has no row locks and merges concurrent transactions cell by cell, so two sessions each doing `next = next + 1` both commit and the counter reads one increment; only same-cell-different-value writes raise a serialization failure ([engdocs/BDP_GRAPH_ARCHITECTURE.md](https://github.com/gastownhall/beads/blob/main/engdocs/BDP_GRAPH_ARCHITECTURE.md)). Anything in beads-ops that counts or sequences must use `--if-revision` CAS, not read-modify-write. Third, criss-cross merges changed semantics in Dolt 2.6.0 and a merge "can leave invalid foreign key state even after conflicts are resolved" ([Dolt conflicts](https://docs.dolthub.com/concepts/dolt/conflicts)); the recovery runbooks under `docs/recovery/` are the answer, and the projection's rebuild-and-diff is your independent check that the Dolt store is sane after a messy merge.

What the graph layer does own across machines is the stale-claim problem that node-local leases leave open. The synthetic coordination study behind grite found duplicate-work rates of 0.78 with no coordination, 0.64 with locks only, and 0.00 with locks plus visible shared state, and concluded "leases alone did not fix" redundant work ([arXiv 2606.19616](https://arxiv.org/html/2606.19616)); BeadHub's author reported that hard locks deadlocked and advisory locks plus a single coordinator role "mattered more than any technical decision" ([BeadHub](https://hn.jakechampion.name/reader/https://juanreyero.com/article/ai/beadhub)). The design that follows is: the *claim event* ("agent X on machine M started issue Y at T") lives in the shared store as `status`/`assignee`/`updated_at` plus a `metadata.claim` record written through `bd update --claim`; the *lease* stays node-local in beads; and a beads-ops lint query over the projection flags `in_progress` issues whose `updated_at` exceeds a project TTL with no journal activity, offering `bd reclaim`-equivalent release via `bd update --if-assignee` so the release is itself CAS-guarded. That query runs identically on every machine because every machine projects the same synced fields.

## Queries and workflow checks are analysis, not a second workflow engine

Beads already answers the operational questions: `bd ready` computes the frontier with atomic `--claim`, `bd blocked` lists blockers, `bd dep tree` and `bd graph` render layered DAGs, `bd dep cycles` and write-time rejection handle cycles, and `bd mol progress` reports completion and ETA ([docs/core-concepts/dependencies.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md)). The projection should not re-implement these as authoritative; `bd ready` remains the arbiter of what is claimable, because its exclusions (in_progress, blocked, deferred, gate-held, custom status categories) are upstream policy that changes between releases. The graph layer's value is the analytic queries that have no `bd` command and that community tools keep rebuilding from scratch: perles wrote its own BQL, paseo-beads-viewer computes "the critical dependency chain," beadcyte models scheduling, and `bv` computes parallel execution tracks via Union-Find over connected components plus PageRank, betweenness, critical path, and Tarjan SCC in "robot mode" ([docs/community-tools.md](https://github.com/gastownhall/beads/blob/main/docs/community-tools.md); [beads_viewer README](https://raw.githubusercontent.com/Dicklesworthstone/beads_viewer/main/README.md)). The concrete query set for beads-ops, in rough priority order, is: transitive blockers of X across all blocking edge types (a Datalog rule); parallel tracks as connected components of the open blocking subgraph, which is the scheduling signal Co-Coder showed lifts pass rate from 56.8% to 68.1% and halves wall-clock while dependency-blind parallelism scored *below* sequential ([arXiv 2606.00953](https://arxiv.org/pdf/2606.00953)); critical path as longest path over `estimated_minutes`, computed in application code with Kahn's algorithm on a single edge-list fetch because Neo4j's own benchmark shows pattern-matching enumeration failing to complete at 50k dependencies while the algorithmic approach takes 51 ms ([Neo4j DAG blog](https://neo4j.com/blog/developer/dags-neo4j-critical-path-analysis/)); subtree completion over `parent-child`; stale and orphan detection; changes since a watermark from the projected events; and impact analysis from `metadata` artifact links to files and PRs, expanded one hop through `blocks`.

Workflow modeling likewise should lean on beads' formula → proto → molecule pipeline rather than a statechart engine of its own. A formula is already a TOML DAG with typed steps (`task|human|gate`), `needs` fan-in, variable validation, and aspect advice; pouring produces a parent epic with hierarchically-ID'd children, and a molecule is a WF-net whose root is the source and "all steps closed" is the sink ([docs/workflows/formulas.md](https://github.com/gastownhall/beads/blob/main/docs/workflows/formulas.md); [docs/workflows/molecules.md](https://github.com/gastownhall/beads/blob/main/docs/workflows/molecules.md)). Classical soundness (every step reachable from the root, completion reachable from every step, no dead transitions) is decidable for ordinary Petri nets and trivially cheap at these sizes ([van der Aalst](https://www.vdaalst.com/publications/p628.pdf)), and beads documents nothing beyond `--dry-run` for formula validation, so a pour-time soundness lint is a genuine gap the projection fills. Per-issue status transitions should be expressed as data (XState's split of JSON-serializable config from implementation functions) and enforced as pre-claim and pre-close lint, with the caveat the modeling note states bluntly: "insert-time enforcement is preferable because agents will not reliably run lint," so wherever beads' own hooks (`.beads/hooks/on_update`, `on_close`) can veto, put the check there and let the projection be the reporting surface. One semantic ambiguity to resolve empirically before writing lint: the dependencies doc says `parent-child` means "Children blocked when parent blocked," the DeepWiki rendering says children of *deferred* parents are blocked, and the FAQ says it has no ready effect; test it against your pinned version and record the answer in the process doc.

## Expose intent-level tools through the CLI first and MCP second

The beads maintainers' own guidance on agent exposure is the right starting point: "For environments with shell access (Claude Code, Cursor, Windsurf), the CLI + hooks approach is recommended over MCP. It uses ~1-2k tokens vs 10-50k for MCP schemas" ([integrations/beads-mcp/README.md](https://github.com/gastownhall/beads/blob/main/integrations/beads-mcp/README.md)). Claude Code reinforces this with a default 25,000-token cap on any single MCP tool result and tool-definition deferral once definitions exceed roughly 10% of context ([xpoz](https://help.xpoz.ai/en/articles/12681842-claude-code-mcp-tool-exceeds-maximum-allowed-tokens-25000); [Aident, 2026-07-22](https://aident.ai/blog/reduce-mcp-token-usage-claude-code-codex)). The beads-ops surface should therefore be a small CLI (call it `bops`) with `--json` output that Claude Code and Hermes invoke from a shell, offering roughly a dozen intent-level commands rather than a raw query tool: `ready` (delegates to `bd ready`), `blockers <id> --transitive`, `tracks`, `critical-path [--mol]`, `subtree <id> --stats`, `changes-since [watermark]`, `impact <path>`, `stale-claims`, `lint-formula <file>`, `lint-claim <id>`, and `lint-close <id>`. Every result is paginated by your own convention (`{items, next_cursor, truncated}`), because MCP cursor pagination applies only to list endpoints, not tool results ([MCP spec: Pagination](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/pagination)); a budget of 20–50 compact rows or a 2–4k-token two-hop subgraph per call keeps well under the cap. A thin MCP server wrapping the same commands, read-only by default in the Memgraph `MCP_READ_ONLY` style ([PyPI mcp-memgraph](https://pypi.org/project/mcp-memgraph/)), serves consumers without a shell; Datalevin's own `dtlv mcp` (read-only by default, stdio, opens the directory directly) is a free fallback for ad-hoc datom-level inspection but should not be the primary agent surface, both because it exposes datoms rather than intents and because a second process opening the directory is the thing to avoid ([Datalevin mcp.md](https://github.com/juji-io/datalevin/blob/master/doc/mcp.md)). The Clojure orchestrator calls the projection as a library and the rules as data; the TypeScript binding calls `bops --json` or the orchestrator's HTTP endpoint, not Datalevin directly, which removes the unverified multi-process question from the design entirely.

All writes, from every consumer, go through `bd` (CLI, `bd serve` HTTP, or the Go library) so that hooks, hash-ID assignment, cycle checks, close policy, and lease arbitration stay upstream's responsibility. Every beads-ops write wrapper takes an idempotency key (the agent's op ULID or `(session, step)`), uses `--if-revision`/`--if-assignee` where the write is conditional, and records `actor`, `session`, and a prompt hash in `metadata` so the journal's actor attribution plus your metadata gives the "which prompt caused this" forensics Yegge cites as the main reason to prefer a graph over a list ([Dark Factory KB on MEOW](https://dark-factory-kb.pages.dev/steve-yegge-meow.html)). Annotate MCP tools with `readOnlyHint`/`destructiveHint` but enforce server-side, since the spec says clients must treat annotations as untrusted ([MCP spec: Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). Pin exact versions of everything marked EXPERIMENTAL upstream (`backend/http`, `OpenBestAvailableWith`, `bd connect`), and build the binding against `--json` with `BD_JSON_ENVELOPE=1` now, since the envelope "will become the default format in v2.0" ([docs/reference/json-schema.md](https://github.com/gastownhall/beads/blob/main/docs/reference/json-schema.md)).

## Conclusion

The question as posed assumed the graph layer would have to carry sync and durability for a file-based tracker; the research shows beads already solved that problem by becoming a Dolt database, and that both upstream and the only surviving JSONL fork learned the hard way how expensive a second canonical store is. That reframes the graph layer from infrastructure into analysis: a Datalog projection whose entire job is to answer the questions `bd` cannot (transitive and cross-type traversal, critical path, parallel tracks, formula soundness, cross-machine stale claims) and to give beads-ops a stable, version-pinned contract against an upstream that reorganizes its storage every few months and is now building its own generic graph store. Built that way, the layer is small enough to delete the day Beads Graph Preview 2 serves issues over BDP, and valuable enough in the meantime to justify its one native dependency.

The two decisions still owed to experiment rather than reading are whether the events journal survives pulls across machines (assume not; re-project after every pull) and the exact ready-effect of `parent-child` on your pinned version. Everything else in this report is decidable now, and the single highest-leverage item is not the database at all: it is the stale-claim lint over synced fields, because v1.3.x leases are node-local by design and nothing upstream will reclaim an `in_progress` bead orphaned by a crash on another developer's machine.
